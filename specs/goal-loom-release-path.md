# Goal — loom has CI, and a merge makes a tag

Mesh goal `loom-release-path`, running.

## Statement

G0, loom's half. loom has no workflows: add CI running go test ./... with a Postgres service container, and tag on merge — every merge to main gets the next minor tag unless it carries a patch label. The bump PRs on consumers are runsheet's half, a separate goal. The brief is runsheet/runsheet specs/proposal-loom-for-adr-001.md (Prologue, project runsheet), section 3. loom has ten consumers (runsheet, wardroom, latchkey, grapevine, optrader, ten99 on v0.49.0; tripline, purser, foghorn on v0.46.0): every change is backward compatible or ships behind an opt-in, and the consumers' adoption is their own goals, not this one's.

## Acceptance

A PR's CI runs the full suite against Postgres and blocks the merge when red; merging a one-line PR produces the next tag without a person; a patch-labelled merge produces a patch tag.

On the 18-core box here the same pool gets 18 and the suite passes in 22s, which is why attempt 1's local verification looked clean. So `v0.0.0` is only the fallback when a repo has no tags. The first automated tag here will be **`v0.50.0`**, or `v0.49.1` if that PR is labelled `patch`. The ADR says this and doesn't restart the numbering. **What I added:** - **`.github/workflows/tag-on-merge.yml`:** set up as the brief asked: - It runs when a PR into `main` is closed, and the job only runs if the PR was merged. - It fetches full history and tags, picks `patch` if the PR has that label and `minor` otherwise, and pushes an annotated tag on the merge commit to `origin`. - Two additions of my own: a concurrency group so two merges close together can't compute the same tag, and a skip if the merge commit already has a version tag. - **`.github/scripts/next-tag.sh`:** the version computation. It finds the latest tag with `git tag --list 'v*.*.*' | sort -V | tail -1`, but first drops anything that isn't exactly `vX.Y.Z` (e.g. `v1.0.0-rc1`). It keeps the step in the workflow short and can be run by hand. - **`docs/adr/0001-ci-and-release-tagging.md`:** has a one-line `summary:` and covers: - the CI gate in `ci.yml` (Postgres 16 service, plus the check that stops the e2e tests from skipping silently); - the minor-by-default / patch-by-label rule and why (pre-1.0 semver); - where numbering starts (the `v0.0.0` fallback, and loom's actual `v0.50.0`); - the link to G0 in runsheet's proposal. **How I checked the acceptance:** I took the tag step's script straight out of the workflow YAML and ran it in a scratch repo with a local bare repo as `origin`, starting with no tags: - A merge with no label produced **`v0.1.0`**. - The next merge, labelled `patch`, produced **`v0.1.1`**, not `v0.2.0`. - Running it again on the same commit did nothing. - `git ls-remote --tags origin` and `git for-each-ref refs/tags` show both are annotated tags pointing at their merge commits. - The workflow's job condition reads `github.event.pull_request.merged == true`. - Against this repo's real tags, the script gives `v0.50.0` for minor and `v0.49.1` for patch.
