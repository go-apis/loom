# Goal — A runner that cannot go on says so, and the rest go on

Mesh goal `loom-runners-fail-loud`, running.

## Statement

G1: projection failure state on the checkpoint row, with backoff and a skip endpoint; lazy decode so a runner decodes only the events it subscribes to, an `@retired` event marker, and Migrate refusing unknown types in the log; an explicit start position for processes with from-head the default for a new one; ERROR on a never-checkpointed runner and failures logged at most once a minute; loom.CloudLogHandler writing `severity` so Cloud Logging's severity>=ERROR finds `runner step failed`. The brief is runsheet/runsheet specs/proposal-loom-for-adr-001.md (Prologue, project runsheet), section 3. loom has ten consumers (runsheet, wardroom, latchkey, grapevine, optrader, ten99 on v0.49.0; tripline, purser, foghorn on v0.46.0): every change is backward compatible or ships behind an opt-in, and the consumers' adoption is their own goals, not this one's.

## Acceptance

Tests: a fold that always fails leaves the runner stalled with the seq and error while other runners advance; a log holding an undeclared type fails Migrate and not the runners; a new process with effects performs none for events before it existed; the handler's JSON carries severity=ERROR for a failed step.

Item 4 is complete on `mesh/loom-runners-fail-loud-4` (commit `50b45d9`). ## What I did **`cloudlog.go`** — new file, `loom.CloudLogHandler(w io.Writer) slog.Handler`: - Wraps `slog.NewJSONHandler` with a `ReplaceAttr` that renames `level` → `severity` (mapped by range to `DEBUG`/`INFO`/`WARNING`/`ERROR` — slog's WARN becomes Cloud Logging's WARNING) and `msg` → `message`. The rename only applies to the record's own built-ins: an application attribute called `level` carries a string rather than a `slog.Level` and is left alone, as is anything inside a group. - A thin `cloudLogHandler` wrapper does what `ReplaceAttr` can't — the trace lives on the context. When `trace.SpanContextFromContext` is valid it adds `logging.googleapis.com/trace`, `/spanId`, `/trace_sampled`. `GOOGLE_CLOUD_PROJECT` (set for you on Cloud Run/GAE/GKE) gives the `projects/<id>/traces/...` form Cloud Logging links on; without it the bare trace id still goes out. `WithAttrs`/`WithGroup` are overridden so the wrapper survives a `slog.With(...)` service logger. - `log/slog` + `os` + `go.opentelemetry.io/otel/trace`, which is already a direct dependency — no Cloud Logging client, no SDK, consistent with DESIGN.md's OTel-API-only stance. - I added a second constructor, `CloudLogHandlerOptions(w, opts)`, because the single-argument form gives no way to set a minimum level (Debug would be silently dropped). A caller's `ReplaceAttr` chains after the mapping. It is opt-in, as scoped: loom's default is still `slog.Default()`, and nothing in the package wires it. **Docs** — DESIGN.md's Observability bullet now names `CloudLogHandler` and what it maps; README's Observability section gets the wiring snippet and the reason (a plain JSON handler's `level` is invisible to `severity>=ERROR`). ## Acceptance `cloudlog_test.go` — seven tests, all passing. - 2026-09-24 · item 2 · Item 2 is done and committed on `mesh/loom-runners-fail-loud-2`. `go test ./...` passes against the local Postgres, including the 22s e2e suite, and I ran the three new tests three times in a row with no failures. **What a failing projection does now** - **It halts instead of retrying forever.** If a projection can't decode, fold or write one event, the events before it are saved and the checkpoint stops just short of it. In the same save, the checkpoint row records `failing_seq`, `attempts`, `last_error` and `stalled_since`. `stalled_since` is set on the first failure only, and `attempts` restarts at 1 if a different event fails. The next step that gets past the event clears all four. - **It backs off.** The wait starts at twice the poll interval, doubles with each attempt and stops growing at five minutes. New events don't wake it early; only a skip or rebuild does. A skip only interrupts the wait on the instance that received the request; other instances finish their current wait. - **Logging is rate-limited.** `runner step failed` logs at most once a minute per runner. It carries the failure count since the last line, plus `failing_seq`, `attempts` and the backoff. `runner never checkpointed` logs under the same limit when a runner has no checkpoint row one poll after `Start`. - **Idle runners now write their checkpoint row.** Otherwise every fresh service with an empty log would log "never checkpointed". The new row never overwrites an existing one, so it doesn't conflict with item 3's head-of-log start for processes. - **New skip endpoint.** `POST /runners/{name}/skip` (Go method `Client.SkipStalled`) accepts the runner name with or without the `projection:` prefix. It first waits for any step in progress, then in one transaction writes the failing event to `loom_dead_letters` and moves the checkpoint past it, clearing the stall. It returns 409 if the projection isn't stalled. - **Visibility.** `GET /runners` now includes `stalled`, `failing_seq`, `attempts`, `last_error` and `stalled_since`. I also added a stalled indicator and a skip button to the console's Issues tab, which the brief didn't ask for. **Things to know** - **Consumers must run `Migrate` before the new runners start.** The four new columns are added with `ADD COLUMN IF NOT EXISTS`, but the runtime now reads and writes them, so an upgraded runner on an unmigrated database will fail. DESIGN.md says this. - **A skipped event can't be redriven.** Redrive for a projection's dead letter still returns "no redrive". To apply a skipped event after all, fix the fold and rebuild. - **The table definition is in `db.go`,** not `stream.go` as the brief says; the new columns went there. **Acceptance tests** (`internal/e2e/stall_test.go`) add a second projection next to billing's `invoiceSummary`, reading the same log, whose fold always errors on `InvoicePaid`: 1. `TestFoldFailureStallsRunner`: the broken projection shows `stalled_since` set, `failing_seq` equal to the `InvoicePaid` event's position, and a non-empty `last_error`. Its checkpoint stays behind that event across attempts while `invoiceSummary` moves past it. `/runners` reports the same. 2. `TestSkipStalledProjection`: the skip endpoint returns the skipped event's position, the stall fields clear, the checkpoint moves past the event, and the event is in dead letters with its error. A second skip returns 409. 3. `TestRunnerFailureLogCeiling`: after four or more failed attempts, `runner step failed` has been logged exactly once. A projection whose lock the test holds the whole time logs `runner never checkpointed` exactly once. Unit tests cover the backoff delays and the once-a-minute limiter. **Docs:** DESIGN.md's Runtime section has a new bullet on the halt behaviour and the console section mentions skip.
